# Deployment

## Local development

See the root [README.md](../README.md#quickstart-local-no-docker) —
`scripts/setup.sh`, `scripts/migrate.sh`, `scripts/seed.sh`,
`scripts/train.sh`, then run the backend and frontend directly.

## Docker Compose

```bash
cp .env.example .env
docker compose up --build
```

`docker-compose.yml` defines three services:

- `postgres` — PostgreSQL 16, healthchecked before `backend` starts.
- `backend` — built from `backend/Dockerfile` with the **repo root** as
  build context (it needs `database/`, `data/`, and `ml/` as sibling
  packages, not just `backend/`). Runs `alembic upgrade head` before
  `uvicorn` on every container start, so migrations are never missed.
- `web` — built from `apps/web/Dockerfile`. **Important**: Next.js inlines
  `NEXT_PUBLIC_*` variables into the client bundle at *build* time, not
  container start — they're passed as Docker build `args` in
  `docker-compose.yml`, not `environment:`. Changing the API URL for a
  Docker deployment means rebuilding the `web` image, not just restarting
  the container.

Mock data and model training aren't run automatically by Compose (seeding
production infrastructure with synthetic data by default would be a
mistake) — run `scripts/seed.sh` / `scripts/train.sh` against the
containerized Postgres afterward if you want mock data to explore.

## Database migrations in production

```bash
DATABASE_URL=<production-url> alembic upgrade head
```

Always review an autogenerated migration
(`alembic revision --autogenerate -m "..."`) before applying it — Alembic
can miss certain changes (e.g. some constraint alterations) and a human
should confirm the generated DDL matches intent.

## Production configuration checklist

- Set real, random values for `JWT_SECRET_KEY` and `APP_SECRET_KEY` (never
  the `.env.example` placeholders — see `docs/SECURITY.md`).
- Set `APP_ENV=production` — this disables the mock-data seed script
  (`database/seed/mock_data.py` refuses to run) as a safety check.
- Point `DATABASE_URL` at a real PostgreSQL instance with a dedicated
  non-superuser role.
- Set `CORS_ALLOWED_ORIGINS` to your actual frontend origin(s), not `*`.
- Set `DATA_PROVIDER_MODE=live` only once a real provider implementation
  is registered in `data/ingestion/providers/registry.py` — otherwise the
  app will error loudly rather than silently serving mock data as if it
  were real (see `docs/DATA_SOURCES.md`).
- Provide real provider API keys only for providers you've actually
  implemented and licensed.

## What's not yet production-ready

- **Single-process WebSocket manager** (`backend/app/websocket/manager.py`)
  keeps connections in-process memory — running more than one backend
  replica means clients connected to different replicas won't see each
  other's broadcasts. A multi-replica deployment needs a shared pub/sub
  (Redis, etc.) behind the same interface — not yet built.
- **No managed background worker** for scheduled retraining/backtesting —
  `scripts/train.sh` is run manually today; a production deployment should
  run it on a schedule (cron, a workflow scheduler) rather than by hand.
- **No CDN/static-asset pipeline** beyond what `next build` produces by
  default.

See `docs/ARCHITECTURE.md#roadmap` for the fuller list of what's built
versus planned.
