# Model Limitations

Read this before trusting, deploying, or extending any model in this
repository. Nothing here is disclaimer boilerplate — each point is a
concrete way the current models can mislead you if used outside what
they've actually been validated for.

## The biggest one: trained on mock data

Every metric in `docs/ML.md` and `docs/BACKTESTING.md` comes from
synthetic data generated by `MockCricketProvider`/`MockFootballProvider`
(`data/ingestion/providers/mock_*.py`), not real matches. The generators
are deliberately built to have the right *statistical shape* for their
respective models (phase-dependent ball outcomes for cricket; team-level
Poisson attack/defense for football) so that fitting and backtesting
exercises real, working statistical machinery — but a model recovering
structure that was deliberately put into synthetic data is a much lower
bar than a model finding structure in messy real-world data. **Do not cite
the accuracy/Brier numbers in this repo as evidence these models would
perform similarly on real cricket or football matches.** They will need
retraining and re-backtesting on real historical data before that claim
can be made, and the numbers will very likely be different (probably
worse — real matches have far more unmodeled variance than the mock
generators).

## Cricket win-probability ensemble

- **No player-quality signal.** The mock training corpus's batters and
  bowlers are drawn from a flat name pool with no skill differentiation, so
  the model has never seen (and cannot use) "this is a strong batting
  lineup" as a feature. A production version needs player-level features
  (recent form, career average, matchup history) that this repo's schema
  supports (`player_venue_stats`, `player_bowler_matchups`, etc.) but the
  current training script does not yet consume.
- **No venue/pitch effects.** All mock matches are played at the same
  fictitious venue.
- **First-innings win probability is a two-stage approximation** (project
  final total, then Monte-Carlo a chase against a bucketed sample of that
  projection) rather than a single joint simulation — reasonable, but
  coarser than directly modeling the full match jointly.
- **The logistic regression is intentionally simple** (no interaction
  terms, no regularization tuning, no XGBoost/LightGBM). This was a
  deliberate choice to keep the first working version interpretable and
  auditable; the spec's suggestion to consider gradient-boosted models is
  a legitimate next step *once there's a real backtest showing they add
  calibrated skill over this baseline* — not before, per "don't choose a
  model merely because it sounds more advanced."

## Football Dixon-Coles model

- **No time-decay weighting is applied by default** (`xi=0` in
  `fit_dixon_coles`) — every training match is weighted equally regardless
  of recency, even though the function supports recency weighting. A real
  deployment should tune `xi` on validation data rather than assume 0 or
  any other specific value is right.
- **The live in-match Monte Carlo simulation assumes goals in the
  remaining minutes are independent of the current scoreline** — it does
  not model a leading team sitting deeper or a trailing team pushing
  numbers forward. This is a known, documented simplification
  (`ml/football/monte_carlo.py` docstring), not an oversight.
- **No player-level goal/assist projection is implemented** — the schema
  (`football_player_stats`) supports it; the model does not yet produce it.
- **No lineup/formation/injury effects** are wired into `expected_goals`
  yet, despite the schema supporting lineups and news-derived
  availability signals.

## General

- **Correlation vs. causation**: nothing in this codebase distinguishes a
  causal effect from a correlation picked up by a statistical fit — e.g. a
  team's attack rating reflects who they played and how they scored, not
  a controlled estimate of "true quality." Treat every rating as
  descriptive of the data it was fit on, not as a causal claim.
- **Small samples**: `ml/feature_engineering/shrinkage.py` exists
  specifically because per-matchup and per-venue aggregates get
  unreliable fast; any feature or UI surface reading directly from
  `player_bowler_matchups`, `player_venue_stats`, etc. without applying
  shrinkage (or at least surfacing `sample_size`) is reintroducing the
  exact problem shrinkage was built to solve.
- **No guarantees, ever.** Every prediction is a probability estimate
  with a `model_confidence` and `data_quality` field precisely because
  sporting outcomes are not deterministic — see the "Core principles"
  section of the root README.
